## MTP Boundary

The same sidecar does not yet support continuous speculative decode:

```text
reports/mtp/a100_mtp_iterative_accept_weighted_math_v3_heldout16_20260517_115852.json
events: 94
accepted: 8
accept rate: 8.51%
```

Each heldout prompt accepts the first token, then mostly diverges on later
tokens. So fc-only calibration is a first-token bridge, not a complete draft
model. The next A100 step is to train/evaluate token+1..N, not just prompt
boundary token+1. Partial unfreeze of `mtp.layers.0.*` is now justified.

## Mainline Decision

Commit these artifacts to mainline because they narrow the 155 TPS route:

1. A100 has a GREEN first-token MTP sidecar candidate.
2. A100 iterative accept proves fc-only is not enough for speculative decode.
3. R6000 confirms the safe serving line is still about 100 TPS.
4. R6000 confirms the 108-109 TPS cuda-tile speed line is not quality-safe.

Next concrete work:

1. A100: train MTP on iterative token positions, starting with partial unfreeze
   of `mtp.fc.weight` plus the MTP attention/MLP layer.
2. R6000: keep Config D as serving fallback; start native grouped active-MoE
   kernel work or MTP integration only after iterative accept improves.
3. Spark: consume only the reusable scripts and proven runtime conclusions;
   do not inherit `cudaTileDown` as a production candidate.

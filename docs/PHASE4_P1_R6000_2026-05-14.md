## Why This Matters

The most dangerous failure mode found earlier was silent corruption: packed
`uint8` weights and FP8 scale tensors could be interpreted as ordinary weights
and allow a model to "load" while producing garbage.

P1 closes that class of failure for this workload:

- BF16 known-good path loads through Lynn engine.
- NVFP4 v8-RTN is recognized as a supported target format but not silently
  executed before dequant support exists.
- The next tensor-level work item is fully specified and has a BF16 oracle.

This is the 0-to-1 step for Lynn engine on R6000: it can now distinguish
"known-good BF16", "known NVFP4 format awaiting P2 dequant", and "unsafe to
run".

The next P2 step is no longer "figure out how to decode NVFP4". It is to expand
the same proven dequant primitive from one tensor to one full Linear group, then
one layer.

Original P2 slow-path dequant sequence:

P2 slow-path dequant sequence:

1. unpack `uint8` packed bytes into two FP4 values per byte,
2. decode FP4 values using the NVFP4 value table,
3. broadcast `weight_scale` with group size 16,
4. multiply by `weight_global_scale`,
5. compare dequantized FP32/BF16 statistics against the BF16 oracle.

Only after one tensor passes should we expand to one Linear, one layer, then
multi-prompt parity. Native NVFP4 GEMM remains out of scope until P3 parity is
green.
